# 发布流程

## 工作流

| 入口                                    | 触发条件                    | 行为                                            |
| --------------------------------------- | --------------------------- | ----------------------------------------------- |
| `.github/workflows/ci.yml`              | PR、手动运行、发布流程调用  | 格式、类型、完整测试与构建；PR 另验收桌面安装包 |
| `.github/workflows/release-desktop.yml` | `desktop-v*` tag            | 检查 → 各平台打包与验收 → Release 草稿          |
| `.github/workflows/release-cli.yml`     | `cli-v*` tag                | 检查 → CLI 打包与验收 → npm 发布                |
| `.github/workflows/build-desktop.yml`   | 手动运行、PR 与发布流程调用 | 按平台构建并验收桌面安装包，上传 Actions 产物   |

临时测试包复用「桌面安装包构建与验收」工作流：在 **Run workflow** 中选择目标分支（如 `feat/multiplayer`），`platform` 选择 `win`、`linux`、`mac` 或 `all`，默认仅构建 Windows x64。安装包上传到对应运行的 `desktop-<平台>-<架构>` Actions 产物，保留 14 天，不创建 Release。手动入口需先随工作流合入默认分支才能使用；PR 和正式发布调用仍默认构建全部平台，签名仅由正式发布流程开启。普通分支 push 不自动打包。

正式桌面 Release 发布或编辑后，`.github/workflows/sync-website-release.yml` 仅按事件中的 Release ID 读取该版本的当前内容，创建或更新官网 `src/content/releases/<版本号>.md`，不遍历历史 Release 或官网文件树，也不自动补齐历史记录。Markdown frontmatter 保存版本、发布日期与来源链接，正文保留 Release 原文；无正文时显示未填写说明。仅当该版本高于官网 `desktopVersion` 时才更新下载版本；编辑旧版说明只更新该版本文件，不会降级下载入口。当前或更新版本缺少任一平台安装包时失败，旧版说明同步不检查安装包。版本变量与当前发布文件的变化通过 Git Trees API 在同一个 commit 中提交到 `joinTARP/web-site` 的 `main` 分支，内容相同则不提交，不修改其他版本文件或列表页 Markdown。草稿、预发布、CLI 发布不触发同步。官网托管平台需已连接该仓库，并启用 `main` 分支 push 自动构建。

已发布版本不需要删除 Release 或移动标签。先合入官网改动，再将同步工作流合入桌面仓库默认分支并配置下述 Secret，随后打开桌面仓库 **Actions → 官网版本与发布记录同步 → Run workflow**，选择默认分支，在 `tag` 填写真实发布标签（如 `desktop-v0.1.1`）后运行。手动入口只读取指定 Release，仍会拒绝草稿、预发布和不符合格式的标签；重复运行不会重复提交。旧标签对应的提交若尚未包含本工作流，编辑该 Release 不会触发新增工作流，使用手动入口补同步即可。不要为启用官网同步覆盖既有发布标签或重新打包。

首次使用需在桌面仓库 Actions Secrets 配置 `WEBSITE_CONTENTS_TOKEN`：使用 fine-grained PAT，仅选择 `joinTARP/web-site`，授予 **Contents: Read and write**，并确保组织已批准该 Token（如需审批）。Token 所属账号需有官网仓库写权限，且 `main` 分支规则允许该账号直接提交。默认 `GITHUB_TOKEN` 仅限当前仓库，不能用于此跨仓库提交。工作流文件须先合入桌面仓库默认分支，官网的 `desktopVersion`、带版本号的链接模板与发布内容集合、列表及详情页也须先提交到 `main`。同一 Release 的任务串行执行，不同 Release 使用独立并发组，避免互相取消排队任务。同步使用官网当前提交作为父提交和基础文件树，非强制更新分支；并发修改导致更新失败时不会覆盖他人提交，可重跑失败任务。同步提交的作者为 Token 所属账号；Token 缺失、过期或写入被分支规则拒绝时，工作流失败，不宣称官网已更新。

发布工作流复用 CI，共用 `.github/actions/setup/action.yml` 安装根级 `packageManager` 指定的 Bun。依赖统一从根目录按 `bun.lock` 安装；共享包随产品构建，官网和剧情模组不参与构建。CLI 兼容性检查与 CLI 发布流程另外安装 Node.js 22.12.0，验证支持的最低版本。第三方 Actions 固定到提交 SHA，升级时同步核对版本。

开发环境安装步骤缓存 Bun 的依赖下载目录，以及 Hutch 下的 `npm/`、`releases/`、`toolchains/`；按操作系统、架构、锁文件与工具链配置区分缓存。命中后仍执行 `bun install --frozen-lockfile`、构建和验收，下载缓存不包含 `node_modules`、项目构建目录、安装包或签名凭据。缓存不可用时按正常流程重新下载。

根级 `bun run typecheck` 和 `bun run build` 由 Turborepo 调度。类型检查、CLI 构建以及桌面 Vite 页面构建可复用成功任务的结果；共享包源码通过依赖任务参与指纹，实际 Bun 版本、操作系统、架构和构建环境变量也参与区分。CLI 打包与测试准备复用同一构建任务。桌面主进程及原生应用始终重新构建，完整测试、打包、签名、公证、分发验收和 npm 发布均实际执行，不以缓存命中替代。

Actions 在开发环境安装步骤恢复并保存 `.turbo/cache`，按系统和架构隔离归档，无需新增 Secret 或远程缓存账号。缓存键包含锁文件、任务配置、提交和 job，后续提交通过前缀恢复已有任务结果，再由 Turbo 决定哪些任务需要重跑。`scripts/tasks.ts` 统一注入实际平台和 Bun 版本；排查时可运行 `bun scripts/tasks.ts run typecheck --force` 强制执行，或用 `--dry=json` 查看依赖和指纹。缓存输出不包括签名凭据、桌面原生应用及已发布的安装包。

GitHub 缓存有分支和 tag 作用域限制，PR 保存的缓存不能由合并后的发布 tag 直接读取；首次发布或新的 tag 可能需要重新下载，同一 tag 重跑可复用已有缓存。默认分支已有的兼容缓存也可供其他分支及发布流程读取。

普通分支 push 不触发检查；创建或更新 PR 时执行仓库检查，通过后调用 `.github/workflows/build-desktop.yml`，构建并验收 Windows x64、Linux x64 和 macOS ARM64 安装包。PR 不传入签名凭据、不创建 Release；安装包作为 Actions 产物保留 14 天。桌面发布复用同一构建与验收流程，并按配置签名、公证；手动运行仓库检查只执行格式、类型、测试与构建。CLI 分发包验收仍在 CLI 发布流程执行。`scripts/release/smoke.ts` 使用独立临时模组与配置，验证分发产物的版本、帮助、模组加载、原生公式计算和退出码。CLI 从 tgz 独立安装后分别使用 Node.js 和 Bun 运行，使用符合类型目录结构的测试资料覆盖 JSON、TOML 与 Markdown 解析，并检查已安装运行依赖的许可文件；桌面则运行各平台打包后的应用，并验证包内 SQLite 驱动与 Kysely 的加载、写入、事务回滚和重开恢复。

## 发布版本

1. 修改目标产品的 `package.json` 版本：桌面为 `apps/desktop/`，CLI 为 `packages/module-cli/`。
2. 从根目录运行 `bun install` 更新根级锁文件，提交 PR，确认检查和桌面分发验收通过后合入默认分支。影响公开行为或模组格式时同步修改官网正文。
3. 从该提交创建并推送对应 tag，版本必须与目标包完全一致：

```sh
# 桌面版本
git tag -a desktop-v0.1.0 -m "发布桌面版本 0.1.0"
git push origin desktop-v0.1.0

# CLI 版本
git tag -a cli-v0.1.0 -m "发布 CLI 版本 0.1.0"
git push origin cli-v0.1.0
```

两种产品独立发布；例如 `desktop-v0.2.0-beta.1` 会创建预发布草稿，`cli-v0.2.0-beta.1` 则发布到 npm 的 `next` 标签，不创建 GitHub Release。发布时重新检查 tag 对应的提交，不临时改写版本。

## 桌面产物与签名

| runner         | 架构  | 产物                               |
| -------------- | ----- | ---------------------------------- |
| `windows-2022` | x64   | ZIP 安装包（setup 与相邻 payload） |
| `ubuntu-24.04` | x64   | tar.gz 安装包                      |
| `macos-15`     | ARM64 | DMG                                |

各平台构建另生成 `.tar.zst` 更新归档（macOS 为 `.app.tar.zst`）与对应通道的更新元数据；更新归档用于分发验收。更新归档、元数据和可选的 `.patch` 差分补丁均以框架原始文件名上传 GitHub Release，供应用内更新使用。Electrobun 2.0.4 官方未发布 macOS x64 core，当前不生成 Intel Mac 安装包。Linux 目标机需要 WebKitGTK 4.1、GTK 3、Ayatana AppIndicator 和 librsvg；Windows 使用 WebView2。

PR 和手动构建的 Actions 产物仅上传安装包，避免把同一应用的安装包与更新归档重复装进下载 ZIP。更新归档仍在 Runner 上生成并参与分发验收；只有发布 tag 触发的构建才额外上传更新归档、元数据和差分补丁，供发布流程汇总。

`electrobun.config.ts` 和 `hutch.config.ts` 固定框架与 Bun 主进程。开发输出在 `out/desktop/dev-<os>-<arch>/`，稳定输出在 `out/desktop/stable-<os>-<arch>/`，附件位于 `release/`。稳定应用外层是自解压安装器，验收程序从更新归档解出真实应用，使用包内 Bun 运行包内 CLI 和 smoke 程序。不得只使用开发机器的 Bun 或从开发目录加载依赖。

SQLite 使用内置 `bun:sqlite`，Kysely 通过共享适配器同步访问；不分发 `better-sqlite3`。QuickJS Wasm 及其运行依赖作为外部文件复制，其他依赖参与打包。SQLite 验收覆盖加载、写入、事务回滚和重开恢复，Wasm 验收实际创建 QuickJS 上下文并执行代码。

macOS Actions 构建始终开启签名。PR 或未配置证书的发布使用免费临时签名身份 `-`；框架在生成更新归档和 DMG 前分别签署真实应用、外层自解压安装器与 DMG，不在归档生成后重新修改应用，避免破坏更新元数据和差分补丁。CI 挂载最终 DMG 校验安装器签名，并从更新归档解出真实应用做签名校验，任一步失败均停止上传。临时签名只保证包的签名完整性，不提供 Apple 开发者身份认证或公证，下载后仍可能受到 Gatekeeper 拦截。

正式签名使用仓库 Secrets `MAC_CSC_LINK`（HTTPS 证书地址或 Base64 P12）、`MAC_CSC_KEY_PASSWORD` 和 `MAC_DEVELOPER_ID`（完整 Developer ID Application 标识）。发布流程在临时钥匙串导入证书，配置 `MAC_DEVELOPER_ID` 后使用正式身份替代临时签名。公证使用 `APPLE_ID`、`APPLE_APP_SPECIFIC_PASSWORD`、`APPLE_TEAM_ID`，映射到 Electrobun 的对应环境变量；无凭据时不提交公证。本机签名仍由 `TARP_CODESIGN`、`TARP_NOTARIZE` 与对应凭据控制。Hutch 当前不自动签署 Windows 安装器，正式发布前按目标环境补充签名。

本机从根目录运行 `bun run dist` 后执行 `bun scripts/release/smoke.ts desktop` 验收稳定包；开发包可使用 `TARP_SMOKE_CHANNEL=dev`。最后一个任务上传以下附件，不自动公开 Release：

- `TARP-<版本>-windows-x64-setup.zip`
- `TARP-<版本>-macos-arm64.dmg`
- `TARP-<版本>-linux-x64-setup.tar.gz`
- `stable-<系统>-<架构>-TARP.tar.zst`（macOS 为 `TARP.app.tar.zst`）
- `stable-<系统>-<架构>-update.json`
- `stable-<系统>-<架构>-<hash>.patch`（构建生成时上传）
- `SHA256SUMS.txt`（校验全部安装包和更新文件）

安装包在汇总时重命名，构建与验收仍使用框架原始文件名。桌面 Release 不额外上传源码包，使用 GitHub 按发布 tag 提供的源码归档；新建草稿的版本说明附上对应源码链接。发布 tag 必须保留，源码归档应包含构建所需的项目源码、脚本和根级锁文件。

## 验收与公开

桌面 `release.baseUrl` 固定为 `https://github.com/joinTARP/TARP/releases/latest/download`，仅跟踪 GitHub 最新正式 Release；CLI 不创建 Release。公开桌面正式版时确认该版本被标记为 Latest，并保留完整更新归档与元数据。草稿与预发布不进入稳定更新源。当前仅开放 `stable` 通道的三段数字正式版本，更新服务额外比较版本号，避免框架仅按 hash 判断差异时将较新安装降级。

客户端检查优先使用 `gh-proxy.com` 前缀代理，失败后依次尝试 `ghfast.top` 和 GitHub 直连；下载从本轮检查成功的线路开始，失败后继续尝试后续线路，不重新获取元数据或变更已选更新。框架报告的错误与抛出的异常都触发回退，所有线路失败时显示错误，下一轮检查重新从首选代理开始。公共代理的速度与可用性不作保证；单条线路的超时仍由 Electrobun 控制，不按下载速度切换。

Electrobun 2.0.4 没有更新源 setter，`createAcceleratedUpdater` 包装其公开的 `getLocalInfo()`，返回包含当前线路 `baseUrl` 的副本，不改写磁盘上的版本元数据；框架的元数据、全量归档和差分补丁请求都通过此方法取得地址。该适配器只在主进程初始化一次，更新服务串行执行检查与下载；升级框架时需复核 URL 获取路径。构建配置仍保留 GitHub 原始地址，框架生成、校验及安装逻辑不变。

`AppUpdateService` 在桌面初始化后异步检查一次，通过桌面 RPC 暴露状态、检查、下载及重启操作；页面轮询状态，不直接请求更新源。检查不会自动下载或安装。下载与重新检查互斥，只有框架确认 `updateReady` 后才允许重启；下载错误保留在状态中，允许重新检查后重试。设置页重启前提交当前设置，主进程再以原生对话框确认；确认后等待聊天、语音、MCP、登录、参考窗口状态及单实例服务清理，再调用框架的更新安装器。普通退出仍走相同清理流程；安装器启动失败时显示错误并退出，用户可重新打开应用重试。

自动化测试使用注入的更新运行时验证版本边界、错误返回、下载状态和重启确认；真实更新安装须使用两个不同版本的稳定分发包验收，不能用开发通道代替。官网的操作说明见[常见问题](https://jointarp.party/docs/reference/faq/#如何更新应用)。

流程完成后，在 GitHub Releases 检查草稿附件、版本说明和源码。在目标系统验收安装、GUI 启动、模组加载、计算及签名，再公开草稿；自动化验收不能替代安装器和 GUI 验证。源码与许可声明随分发产物提供，正式版公开后由官网同步工作流在同一提交中更新玩家下载版本与更新记录，检查对应提交与官网部署结果。

## CLI 自动发布到 npm

推送 `cli-v*` tag 后，工作流先检查版本、打包并在 Node.js 与 Bun 下独立安装验收，再将同一份 `packages/module-cli/out/tarp-module-cli.tgz` 直接发布到 npm，不创建 GitHub Release，也不生成额外源码包或校验附件。包名为 `@jointarp/module-cli`，公开访问；正式版本使用 `latest`，带预发布标识的版本使用 `next`。npm 包会在流程成功后立即公开。CLI 工作流仅需仓库内容读取权限，发布使用 `NPM_TOKEN`；保留对应 `cli-v*` tag 作为版本源码入口。

首次使用前完成以下配置：

1. npm 账号拥有 `@jointarp` scope，并有权发布 `@jointarp/module-cli`；首次发布时 Token 的权限需要覆盖新包创建。
2. 在 npm 创建 Granular Access Token，授予目标包或 scope 的发布写权限；启用用于无人值守发布的 2FA bypass，并设置合适的有效期。
3. 在 GitHub 仓库 `Settings → Secrets and variables → Actions` 添加 `NPM_TOKEN`。工作流仅在凭据检查和发布步骤读取它，不将其写入下载缓存。
4. 修改 CLI 版本并同步根级锁文件，合并 PR 后推送完全一致的 tag。发布成功后可用 `bunx --bun @jointarp/module-cli@0.1.0 --version` 验证目标版本。

工作流使用 Bun 发布，无需 npm CLI。缺失 Token、权限不足、Token 过期或同版本已存在均会使任务失败；不会跳过失败并宣称已发布。

构建或上传失败可重跑失败任务，Actions 中间产物保留 14 天。已有草稿可重跑更新同名附件，已公开版本拒绝覆盖；修复源码或产物时发布新版本，不移动已发布 tag。npm 同名同版本不可重复上传。
