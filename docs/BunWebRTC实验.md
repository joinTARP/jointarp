# Bun WebRTC 实验

## 结论

2026-10-26，使用纯 TypeScript 实现 `werift@0.25.2`，已在 Bun 主进程完成 WebRTC 数据通道、RPC、订阅取消和二进制传输验证，不需要 WebView 建立网络连接，也没有加载原生 `.node` 模块。

跨机器实验由本机 Mac Bun 与 Linux x64 Bun 直接通信：双方先通过 STUN 收集公网映射，只在 SDP 中交换 `srflx` 候选，然后由 ICE 建立 UDP 连接，DTLS/SCTP 承载数据。没有配置 TURN、使用 SSH 端口转发或手工添加端口映射。

本次选中路径为本地 `host` / 远端 `srflx`，协议 UDP，连接和 ICE 状态均为 `connected`。ICE 的本地候选类型可以是 `host`，不能仅凭本地候选名称否定 NAT 穿透；本实验限制了远端可用候选，并确认数据没有经过中继。

Linux 网卡是云主机私网地址，通过云平台公网映射对外通信。本次结果证明当前 Mac 网络与该云映射环境可连通，不能代替两条家庭宽带、手机 CGNAT 或严格 NAT 的组合实测，也不能推断 NAT 类型或穿透成功率。正式游戏入口未切换。

## 国内 STUN 实测

以下结果均从本机测试。候选地址参考 [uip 的中国 STUN 列表](https://github.com/dndx/uip#servers-in-china)及 [rustp2p-core 的 STUN 示例](https://docs.rs/rustp2p-core/latest/rustp2p_core/stun/index.html)，可用性以下表本次测量为准。

| 地址                               | 独立 UDP Binding 请求 | RTT，两次  | werift 候选收集      |
| ---------------------------------- | --------------------- | ---------- | -------------------- |
| `stun:stun.miwifi.com:3478`        | 2/2 成功              | 92 / 35 ms | 取得 `host`、`srflx` |
| `stun:stun.chat.bilibili.com:3478` | 2/2 成功              | 93 / 34 ms | 取得 `host`、`srflx` |
| `stun:stun.hitv.com:3478`          | 2/2 成功              | 71 / 39 ms | 取得 `host`、`srflx` |
| `stun:stun.qq.com:3478`            | 0/2，超时             | —          | 未选用               |

独立请求校验 Binding Success Response、事务 ID 和地址映射属性，不以 DNS 解析或发送 UDP 成功作为可用证据。本机请求 Cloudflare 和 Google STUN 均超时；同一 Linux 开发服务器请求它们成功。此外，本机对该 Linux 服务器临时单次 STUN 响应器的请求成功，说明不能由上述超时推断本机所有 UDP 均被阻断。临时响应器已退出，没有部署常驻 STUN 服务。

当前默认使用小米节点，可用 `TARP_WEBRTC_STUN` 指定其他节点。当前 werift 解析配置时只选取首个 STUN 地址，实验一次选择一个服务，未实现自动主备切换。上述第三方节点的实测可用性不代表长期服务承诺；当前正式配置没有写入这些地址。

## 运行

从客户端仓库根目录执行，依赖只列入桌面开发依赖：

```sh
# 本机两个独立 Bun 进程，验证实现及数据通道，不算公网穿透。
bun apps/desktop/scripts/bun-webrtc-probe/run.ts local

# 本机双进程收集公网候选；可能仍选中本地路径，不算跨网络验收。
bun apps/desktop/scripts/bun-webrtc-probe/run.ts stun

# 更换本机/本机子进程使用的 STUN 节点。
TARP_WEBRTC_STUN=stun:stun.chat.bilibili.com:3478 bun apps/desktop/scripts/bun-webrtc-probe/run.ts stun

# 与已授权的 Linux x64 开发服务器测试；linux-dev 替换为 SSH 别名。
bun apps/desktop/scripts/bun-webrtc-probe/run.ts remote linux-dev
```

远程模式交叉编译独立 Linux 程序，上传到 `/tmp/tarp-rtc-probe.*`。服务器无需安装 Bun 或 Node，不注册系统服务、不修改防火墙。SSH 标准输入输出仅交换一次 SDP，之后不再收发信令；RPC 和二进制数据只通过 WebRTC。完成后关闭连接并清理远程实验文件。远端程序最多存活 60 秒；强杀本机程序时仍可能需要人工清理临时文件。

运行结果只打印候选类型和状态，不打印 SDP、ICE 密码或具体候选地址。出现没有 `srflx` 的情况会直接失败，不回退成局域网成功。远程 Linux 程序使用默认小米 STUN，本机可通过环境变量单独调整节点。

## 已通过的检查

- Bun 1.4.2 两个独立进程建立 ICE/DTLS/SCTP 数据通道；使用桌面开发包内嵌 Bun 1.4.0 执行同一独立实验亦通过。
- 大帧中文 RPC 往返一致，三条订阅事件有序到达并正常结束。
- 单条订阅取消传到房主，事件生成停止，共享连接仍可继续请求。
- 独立可靠有序数据通道完成 2 MiB 二进制传输，16 KiB 分块，逐字节一致。
- 使用国内 STUN 完成 Mac 到 Linux 的公网候选连接，上述 RPC 和二进制行为通过。
- 通用分帧适配器原有的超限、截断及错误流隔离检查仍通过。

`channel-stream.ts` 将 DataChannel 适配为有界字节流，复用已有实验的 `StreamPort`，发送时执行背压，接收缓冲超限关闭通道。RPC 和二进制分别使用独立数据通道。本实验不传输真实游戏资料，也不代表图片下载、完整房间同步或玩家身份授权已经接入。

后续仍需验证两条真实玩家网络、与浏览器实现的互通、实际 Electrobun 打包生命周期、跨平台桌面、资源传输性能以及玩家中继。先完成这些证据，再决定正式传输选型；当前不移除旧 WebRTC 或 libp2p 实验。

## 原生实现本机对比

2026-10-26，新增 `node-datachannel@0.33.4` 开发依赖，使用其 macOS ARM64 预编译原生模块；底层 `getLibraryVersion()` 返回 libdatachannel `0.24.5`。本次仅操作本机，没有连接或修改服务器。

```sh
# 原生 WebRTC 的本机 RPC、订阅与取消自检。
bun apps/desktop/scripts/bun-webrtc-probe/native.ts
```

原生模块在 Bun 1.4.2 中加载、建立连接和清理退出均成功。原生端点复用同一份分帧与 RPC 检查，通过大帧中文往返、有序订阅、订阅取消和取消后共享连接存续。构建实验时将 `node-datachannel` 保留为外部模块，构建产物也已通过桌面开发包内嵌 Bun 1.4.0 的同一组检查。

该构建测试仍从本地依赖目录加载原生模块，不代表正式 `.app` 已包含所需插件。完整安装包的原生文件复制、模块解析、签名与 Windows/Linux 支持尚未验证。

### 测量条件

使用同一临时驱动分别加载 werift 与原生实现，每次启动新 Bun 1.4.2 进程，交替串行执行三轮。每轮在同一进程创建两个端点，传输 32 MiB，按 16 KiB 分块，256 KiB 发送背压阈值，满缓冲时按 5 ms 间隔检查；接收端核对全部二进制块。另一条可靠有序通道每次等待 ping 回应后间隔 10 ms 再发，用于观察传输对小消息的影响。测试不使用 STUN/TURN，不加载真实游戏数据。

CPU 使用 `process.cpuUsage()` 统计进程全部线程，包含发送端、接收端与校验驱动；100% 表示一个 CPU 核心。以下数值为三轮结果的中位数，不能直接当成单个玩家端的资源用量。

| 指标                               | werift      | node-datachannel |
| ---------------------------------- | ----------- | ---------------- |
| 满速吞吐                           | 19.62 MiB/s | 51.34 MiB/s      |
| 满速时合计 CPU                     | 1.22 核心   | 2.97 核心        |
| 相同 10 MiB/s 负载时合计 CPU       | 0.79 核心   | 1.10 核心        |
| 相同 10 MiB/s 负载时小消息 RTT P95 | 1.18 ms     | 0.85 ms          |

满速时原生实现的小消息 RTT 也出现明显上升，各轮 P95 约 90–112 ms；对应 werift 为 17–18 ms。原生满速阶段较短，每轮只有 9–11 个并发 ping 样本，不能将该 P95 视为稳定统计或直接比较实际玩家延迟。限制为相同 10 MiB/s 后，每轮约 300 个 ping 样本，原生延迟略低。更高吞吐不等于更低 CPU，也不意味着大文件满速传输不会影响交互。

结论：原生方案在当前本机短测中吞吐约为 werift 的 2.6 倍，值得作为正式候选；需要为资源传输设置限速，并继续验证稳定性和安装包集成。尚未进行原生实现的公网 NAT 测试、浏览器互通、多人与长期运行测试，不能据此直接替换正式网络入口。性能驱动按测试维护约定在测量后清理，仅保留功能自检和本节参数、结果。

## 正式主进程接入

已选择 node-datachannel 作为正式传输依赖。`apps/desktop/src/main/online/native-peer.ts` 提供单玩家连接：交换受限 SDP/ICE 信令、可靠有序数据通道、oRPC MessagePort、大消息分块、有界缓冲、握手超时和连接清理。候选可先于 SDP 到达；单个连接关闭不会执行原生库全局清理。

调用方必须先完成房间准入和身份验证，再绑定受限房间 RPC；传输层本身不授予游戏权限。STUN 列表由调用方明确传入，不内置收费 TURN 或服务凭据。当前不实现 ICE 重启，断线后需要重建连接。

桌面构建将 node-datachannel 作为外部依赖，携带当前平台原生包；分发 smoke 增加真实原生通道收发检查。macOS ARM64 开发包的运行时复制到独立临时目录后，已通过应用内嵌 Bun 1.4.0 的加载与通道收发验证。尚未验证签名发布和 Windows/Linux 分发。

### 房间接入

`online/coordinator.ts` 独立实现公开协调协议 v1，不导入私有服务实现。默认地址为 `https://online.jointarp.party`，可通过主进程环境变量 `TARP_COORDINATOR_URL` 改为其他 HTTPS 服务；仅本机回环允许 HTTP。中心只交换临时房间登记和 SDP/ICE，不经过游戏资料。客户端当前仅提取 STUN 配置，未启用收费 TURN。

协调层放行的是受限加密握手。玩家在 P2P 通道内提交公钥身份签名后，仍需要房主审批；未获批连接不能读取游戏和资源。私钥仅保存在本机 `room-identity.json`，不发送给房主。签名覆盖玩家 ID、冒险 ID、随机挑战和双方 DTLS 指纹与 ICE 标识计算出的连接绑定，拒绝跨连接、跨房间及跨玩家重放。内网也使用一次性挑战签名，公钥指纹与冒险内玩家身份固定。开发阶段不迁移旧 secret 身份文件。审批、持久身份验证、房间访问限制及模组发布与内网共用实现；单个连接的身份不可更改。相同身份建立新连接时替换旧连接，旧连接的关闭事件不能撤销新连接授权。

`online/rooms.ts` 将正式游戏 Router 接到原生通道，`lanForwarder` 继续为界面转发远程房间请求。模组和图片使用独立可靠有序资源数据通道的受限 RPC，每块最多读取 256 KiB，最多预取四块；同一资源的并发读取在房主串行执行以保持顺序；资源句柄每连接最多 4 个，空闲 30 秒回收，支持取消与 ETag。资源使用 oRPC 支持的 Blob 二进制编码，复用哈希校验、差量缓存和本机图片入口。互联网资源本阶段不压缩，不经 HTTP 回环或 WebView 转发。

分帧上限为 16 MiB，覆盖现有最大 10 MiB 状态帧的 Base64 编码及 RPC 信封；队列最多 32 MiB，发送按 16 KiB 分块并等待背压。接收分配有界目标缓冲，避免大帧逐片拼接导致反复复制。资源与游戏共用 PeerConnection，但使用各自的数据通道和发送队列；资源通道每连接上限 2 MiB/s，仍共享底层拥塞控制，不承诺弱网下完全不影响游戏。尚未测量公网大文件对交互的影响。

本机测试替身验证：保留前导零的六位码、取消与重新申请、审批前拒绝游戏读取、拒绝身份冒用与跨房/房主操作、2 MiB 图片与缓存、资源取消、客户端重建后的身份和个人笔记恢复、协调断开后的聊天和资源读取，以及开房失败回滚。另有原生通道测试覆盖最大状态帧编码载荷。

房主在加密通道建立后给出 15 秒身份认证期限，首次合法申请后改为固定审批截止时间；轮询不延长期限。批准时先绑定玩家上下文再授权，拒绝后短暂保留结果供界面读取并关闭通道。超时或连接关闭会释放原生端点和协调层名额。

当前没有自动信令重连或 ICE 重启。协调断开时隐藏不可确认的房间码并显示错误，已建立直连继续运行；需要新玩家入房时由房主停止并重新开放，掉线玩家的远程会话标记为断线，取消资源请求并显示重入提示；游戏请求保持远程隔离，不回落到本机房主路径。重新输入房间码时创建新连接而非复用旧通道。玩家中继、收费服务器中继、跨网络 NAT 与长时间多玩家负载仍未验收。桌面回归使用本机协调测试替身，线上协调服务的部署与冒烟检查单独进行。

客户端还已与本机运行的真实独立 Bun 协调实现互通：使用回环监听和内存 SQLite 完成创建、加入、审批协商及原生通道收发；没有修改私有实现，也未将其导入正式源码或长期回归。完整平台回归 573 项通过，桌面类型检查、构建与独立目录运行时验收通过，官网指南构建通过。2026-10-26 已部署线上协调服务，并通过正式域名的开房、审批、双向信令、心跳、权限、ICE 配置和关房冒烟检查；此检查不建立 WebRTC 连接，真实跨网络表现仍未验证。

房间开放只要求冒险处于进行中，不要求开局或开场完成。内网和互联网共用此检查，玩家可提前入房读取资料并参与准备；远端仍不能调用房主专用的开局方案选择和开场重试入口。
